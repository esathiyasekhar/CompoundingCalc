01

Purpose and principles

A planning tool for the Technofunda core + satellite approach: two pots compounding at their own rates, a goal, yearly course correction, and a lesson in starting early.

Rules the code follows

  • No server. Plain HTML, CSS and JavaScript. It runs from local files or as a web page, offline, with no build step.
  • One engine. Every number comes from calculator.js, which has no access to the page. The interface only reads inputs and draws results.
  • Same timing everywhere. One cash-flow timing rule (chapter 3) is used for the schedule, the IRR, the goal solvers and the review.
  • Answers are checked by putting them back. Every solved SIP or return is fed into the schedule again and must reproduce the target.
  • Indian conventions. Lakh/crore grouping, ₹ throughout, financial years shown as 2024–25.
  • The user owns the data. Data stays in the browser or in a file the user chooses.

The update cycle

Every input fires updateAll(), which builds the parameter object, calls the engine with the user's year-end records (planActuals(): state.actualsHistory, or none while a preset is shown), and redraws the Core engine, Goal & schedule, Annual review and spouse comparison. The Youngster lab has its own updateYoungsterLab(). The goal, comparison and review solvers rerun the full schedule a few hundred times per update, which is still instant.

Presets

A preset is data, not code: applyPreset(id) saves the current inputs for Undo, writes the preset's Core engine, goal and Youngster inputs into the form, sets state.presetId, opens its page and shows the presenter note. While state.presetId is set, planActuals() returns no records, so demonstrations are not mixed with the selected user's history; closing the note, Reset page or opening a user clears it. A preset also sets the INF_ADJ view (today’s rupees) (real: true turns it on; otherwise off) and, for goal presets, the goal’s inflation switch (goal.inflationAdjusted). Presets never save anything.

03

Calculation model

Annual steps, two pots, no rebalancing. Year 0 is the start; years 1 to 60 are computed whatever the horizon.

Year 0

L = self lump + spouse lump (if spouse on) core₀ = L × c c = core allocation, s = 1 − c sat₀ = L × s invested₀ = L

Monthly SIP in year y

steps = max(0, min(y, stopStepUp) − 1) pct mode: M(y) = M₁ × (1 + g)^steps ₹ mode: M(y) = M₁ + a × steps year 1 = base SIP; last rise in year stopStepUp

Months of SIP in year y

m(y) = 12 if y ≤ N N = SIP years = extra months (0–11) if y = N + 1 = 0 after that A(y) = M(y) × m(y) money added in year y

Timing weight

SIPs arrive through the year, so they earn only part of the year's return. A full year of monthly SIPs is treated as invested at mid-year; a part-year of m months starting in month 1 has its centre earlier.

w = 0.5 for a full year (m = 12) w = 1 − m / 24 for m months (1–11) This matches the source spreadsheet's semi-annual rule (additions at month 6).

Each pot, each year

core_add = A × c growth_c = core_open × r_c + (A × w) × c × r_c core_close = core_open + core_add + growth_c sat_add = A × s growth_s = sat_open × r_s + (A × w) × s × r_s sat_close = sat_open + sat_add + growth_s corpus = core_close + sat_close invested = invested_prev + A multiple = corpus / invested

Self and spouse money is added together into the same two pots; each keeps its own weight w. Nothing moves between the pots.

Recorded years (actuals)

  • Invested: if recorded, it replaces that year's planned SIPs (split between self and spouse in the planned ratio) with w = 0.5.
  • Core / satellite value: the recorded year-end values replace the model's closes. Growth becomes close − open − added, so the next year starts from the real values.
  • Only a total value: it is split in the model's core/satellite ratio for that year.
  • Older records with returns instead of values are still honoured (per pot or blended).

Years to next 2× and milestones

Both use log interpolation between year-ends, which is exact for constant growth within a year:

year reaching T = (k − 1) + ln(T / V_(k−1)) / ln(V_k / V_(k−1)) k = first year with V_k ≥ T

Milestones are multiples (2×, 4×, … up to 131,072×) of the combined lump sum, or of year-1 additions when there is no lump sum.

Spouse comparison

The plan is run twice: spouse off and spouse on. The strip shows both corpora and amounts invested, the extra corpus, and the fractional year when the combined plan reaches the self-only horizon corpus (time saved = horizon − that year).

04

Return measures

Blended CAGR

blended = c × r_c + s × r_s 70% × 15% + 30% × 25% = 18%

Portfolio IRR

The annual rate R that sets the net present value of the plan's cash flows to zero, with each contribution at its real time:

flows: −L at t = 0 −A_self(y) at t = y − w_self(y) −A_spouse(y) at t = y − w_spouse(y) for y = 1 … horizon +corpus at t = horizon solve Σ cf × (1 + R)^(−t) = 0 Newton–Raphson from 15%; bisection fallback in (−95%, 2000%)

With full-year SIPs (t = y − 0.5) this equals the spreadsheet's semi-annual IRR annualised, (1 + r)² − 1. The IRR exceeds the blended CAGR because the pots are not rebalanced: the satellite's share of the money rises every year, so the portfolio's effective rate drifts towards the satellite rate.

Doubling

money doubles every = ln 2 / ln(1 + IRR) next doubling horizon = years to next 2× measured from the horizon value rule of 72 (shown for comparison) = 72 / (IRR × 100)

Share-of-corpus markers (25 / 50 / 75%)

For p in {0.25, 0.5, 0.75}, the chart marks yearReaching(rows, p × corpus_horizon). The headline sentence uses the 50% year and the years left after it.

Today’s rupees (inflation-adjusted values)

When params.realInflation = i > 0, calculateSchedule runs the normal (nominal) year loop and then divides every value by the inflation factor at the time it occurs:

D(t) = (1 + i)^t open_r = open / D(y − 1) added_r = added / D(y − 0.5) close_r = close / D(y) growth_r = close_r − open_r − added_r so every row still adds up invested_r = lump + Σ added_r IRR flows: cf / D(t) ⇒ real IRR = (1 + IRR) / (1 + i) − 1 exactly blended CAGR shown = (1 + c·r_c + s·r_s) / (1 + i) − 1

Doubling times, milestones and the 25 / 50 / 75% markers are then computed from the real series, so they are real too. calculateYoungsterWealth does the same with realInflation and a yearOffset (a delayed start of d years is deflated from today, not from its own start). The app passes realInflation only when the INF_ADJ view (today’s rupees) is on; the Annual review always runs nominal.

Inflation-adjusted goal

With “Target in today’s money” on, the goal solvers run on the plan in today’s rupees (realInflation = i), so the target is compared with real wealth at every year. This is the same as growing the target with inflation, and it gives the year, SIP and CAGR for an inflation-adjusted freedom number. Displayed corpus values still follow the INF_ADJ view (today’s rupees). The Annual review compares actual values with the target grown to the deadline: target × (1 + i)^years.

Return achieved in the Annual review

A Modified Dietz return that uses the model's own timing, for the whole portfolio and each pot:

growth = close − open − added return = growth / (open + added × w) w = 0.5 for recorded years

Youngster lab mix

Core+SAT doubling time solves c(1 + r_c)^t + s(1 + r_s)^t = 2 for t by bisection; “₹1 L in 30 yrs” is 1,00,000 × the same expression at t = 30. Fixed deposit (6.5%) and Nifty 50 (13%) are fixed reference rows.

05

Solvers

All solvers search over the full schedule with monotone bisection (50–60 halvings), so they respect step-up, stop years, months, spouse money and recorded years exactly.

Keeping the core–satellite gap

When a solver changes “the return”, it moves both pots together and keeps the user's spread (satellite − core):

spread = r_s − r_c r_c' = b − s × spread r_s' = b + c × spread so c × r_c' + s × r_s' = b exactly

Goal: SIP needed on time

  1. Set the horizon to the goal deadline and the rates to the assumed blended CAGR (default: the plan's).
  2. If the plan with no SIP already reaches the target, the answer is ₹0.
  3. Start the upper bound at max(₹10,000, target ÷ (years × 12)) and double it until it reaches the target (cap ₹10¹⁰). If it never does, report “not reachable” (the SIP stops too early).
  4. Bisect the starting monthly SIP between 0 and the bound.

Goal: CAGR needed with current SIP

Bisect the blended return between −50% and 150%; outside that range report “over 150%” or “below −50%”.

Goal: year reached

yearReaching on the current plan's 60-year rows; null means not within 60 years.

CAGR comparison table

Blended rates 12, 15, 18, 20, 23, 26 and 30%, plus the plan's and the assumed rate. For each: rates by the gap rule, the full schedule (with actuals), IRR, doubling time, corpus at the horizon, goal year and the SIP needed on time.

Annual review: course correction

OutputMethod
Revised projectionSchedule with all recorded years, plan after the latest one.
Return needed from hereBisect the blended return for the remaining years (recorded years fixed), −50% to 150%.
SIP needed, scale modeUsed while planned SIP remains (since 1.15 including the extra months of the last SIP year). Multiply every future planned SIP by a factor k (keeping step-up and stop year) and bisect k. Shown as k × next year's planned SIP.
SIP needed, restart modeUsed when the planned SIP has ended. A flat monthly SIP from next year to the goal year, bisected.
Revised goal yearyearReaching on the revised rows.

Past years are never changed by a correction. The goal horizon (not the Core engine horizon) is used throughout this page.

Youngster lab

Same yearly rule as the Core engine, with the tab's own three sliders (core allocation, core CAGR, satellite CAGR) as two pots without rebalancing.

lump L at the current age: core₀ = L × c, sat₀ = L × (1 − c), invested₀ = L horizons h₁ < h₂ < h₃ (years from now, set on the cards; h₃ ≤ 100 − age) checkpointAges = age + h; targetAge = age + h₃ horizon = targetAge − current age checkpoints[i] = { age, corpus, invested, multiple } null corpus if the age is not after today

The horizons live in state.youngHz. The master control moves all three by the same number of years; each card’s −/+ moves one, kept in order by fitHorizons(). Delay scenarios rerun the model from age + w, + 2w and + 3w (w = 3, 5 or 10, chosen on the page) with the same lump sum and SIP settings (one level only), and report the loss at the last age in rupees and %.

Build and release

Two small Go programs, cross-compiled for 64-bit Windows:

  • Compounding Calculator.exe (launcher): opens app\index.html in Edge (--app=file:///…), else Chrome, else the default browser.
  • CompoundingCalculator-Setup.exe: embeds the launcher, icon and the whole app\ folder (including manual\) with embed.FS. Per-user install, no admin.

Start menu and desktop, created by PowerShell.

Web edition

The same four files plus manual/, published as a web page. The page adds a small adaptation layer before calculator.js:

  • Hides CSV, PDF, schedule CSV and Export users (downloads and printing are blocked there).
  • Turns off the database file (no file pickers).
  • Replaces confirm() with “click again within 6 seconds”, and alert() with a message bar.
  • Defaults to the dark theme.

Release checklist

  1. APP_INFO in app.js: version, date, history entry.
  2. Static fallbacks in index.html (data-app="version" and data-app="date").
  3. The version stamp on every file address: ?v= on styles.css, calculator.js and app.js in index.html, the app-version meta tag, and manual.css, manual.js and images in both manuals. Browsers keep files they have seen before; a new stamp makes them fetch the new version instead of mixing old and new.
  4. appVersion in the setup program and assemblyIdentity version in manifest.xml.
  5. Version and date on both manuals; rebuild the PDFs.
  6. Run the tests (chapter 9), rebuild the installer, republish the web edition.

Testing

Verification rules

  • Put the answer back: a solved SIP or return is run through the schedule and must reproduce the target (agreement about 0.001%).
  • Spreadsheet parity: solveIRR with mid-year flows equals the semi-annual IRR (solveSemiAnnualIRR) annualised.
  • Limits: 100% core at 20% in the Youngster lab equals the single-rate model (₹491.80 Cr at 70 for the defaults).
  • Browser check: open every page in Chromium at desktop and phone widths, both themes; no console errors; no sideways scrolling; Reset page and Undo on every page; database file round trip; print preview.

10

Limits and extending

Model limits

  • Constant returns every year; no volatility or sequence risk except through recorded years.
  • No rebalancing between core and satellite (by design, matching the method).
  • No inflation, tax, costs or withdrawals.
  • Annual steps with a mid-year rule for SIPs, not monthly compounding.
  • Data lives per browser unless a database file is used; the database file needs a Chromium browser.

Adding an input to the plan

  1. Add the control to index.html with a stable id and a label.
  2. Cache it in els, read it in getCurrentParams() and listen for input → updateAll().
  3. Use it in calculateSchedule() and add a default there.
  4. Add it to defaultPlanParams(), readInputsForProfile() and applyParamsToInputs() so it saves, loads and resets.
  5. Add a test case and update both manuals.

Adding a preset

Presets live in PRESET_GROUPS in app.js. Each item has an id, title, sub (menu line), tab to open, note (talking point) and any of: core (built with corePreset({...}), Core engine inputs in screen units), goal ({target, years}) and young (built with youngPreset({...})). Add the item to a group and to the table in the User manual. Check its figures with the engine before using it in a talk.

Adding a page

Add a tab-btn with data-tab and a matching tab-panel; give it an update function called from updateAll(); add its case to resetPage(); add an entry to HELP_SECTION and a chapter with that id in the User manual.

Conventions
